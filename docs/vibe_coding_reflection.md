# Vibe Coding 开发过程反思

## 一、使用 Vibe Coding 的整体感受

本项目采用 AI 辅助开发的方式完成，但开发过程并不是简单地把需求复制给 AI 后等待完整答案。更接近的方式是先把项目需求拆成多个阶段，每个阶段只解决一个相对明确的问题：先让项目能运行，再补静态分析，再重构 Agent，再接入 Ollama，再做页面交互、RAG 问答、双仓库对比、测试配置和文档材料。

这种开发方式对工程原型开发比较有帮助。GitHub 仓库智能分析器本身涉及的内容比较杂，包括 GitHub API、git clone、AST 静态分析、Streamlit 页面、Ollama 本地模型、多 Agent、RAG、报告导出和测试配置。如果全部从零手写，容易在某个细节上卡很久。AI 的作用主要是把基础代码、目录结构和候选实现快速搭出来，让我能更早进入“运行、观察、修改”的循环。

不过，Vibe Coding 并不等于自动完成项目。AI 生成的代码需要不断运行验证，页面效果也必须实际打开看。尤其是项目要求强调“不能只是 LLM 总结仓库”，这就要求我在设计上做取舍：哪些内容必须由确定性工具分析，哪些内容适合交给 LLM 总结，哪些地方需要保留降级方案。这个判断不能完全交给 AI。

## 二、Vibe Coding 的优势

第一个优势是搭建速度快。项目早期需要建立 `app.py`、`src/`、`docs/`、`tests/` 等目录，还要写 `.gitignore`、`requirements.txt`、README 和多个分析模块。AI 可以根据题目要求快速给出一个比较完整的初始骨架，我再根据本地运行情况逐步调整。

第二个优势是适合做模块化拆分。比如文件树分析、技术栈识别、代码质量分析、文档完整性检查、安全风险检查本质上是不同的小模块。通过 Prompt 明确输入和输出后，AI 能比较稳定地生成函数结构和返回字段，后续再由 Agent 层统一调度。

第三个优势是调试效率高。开发过程中遇到过 Ollama 接口 404、GitHub API 403 限流、pytest 误收集被分析仓库中的测试文件、双仓库对比雷达图字段类型不一致、Windows 删除 `.git` pack 文件权限不足等问题。把错误信息和当前现象发给 AI 后，通常能快速得到排查方向。

第四个优势是文档生成效率高。项目除了代码，还需要 README、设计文档、技术说明、技术报告和产品介绍材料。AI 能根据已有代码和项目结构生成初稿，再由我检查是否存在夸大、空话或和实际实现不一致的地方。

## 三、Vibe Coding 的局限

AI 最大的局限是容易默认“能跑”，但实际环境可能并不满足。比如 Ollama 未启动、模型名称不存在、GitHub API 被限流、Windows 文件权限阻止删除 `.git` 对象，这些问题都需要在本地实际运行后才能发现。项目最终必须通过真实命令验证，而不是只看代码看起来合理。

第二个局限是 AI 有时会把功能说得过满。比如依赖健康度如果没有接入真实漏洞数据库，就不能写成“已检测出真实 CVE 漏洞”；测试覆盖如果只是检查是否存在 `tests/`，也不能写成真实覆盖率。这里需要人工把表述改成准确的“结构性检查”或“规则估计”。

第三个局限是前端体验需要反复肉眼检查。Streamlit 页面一开始虽然能展示分析结果，但右侧信息太密、左侧区域空、文件树堆在一行、风险列表滚动体验不好。这些问题只有实际使用页面时才明显，AI 无法仅凭代码完全判断使用效果。

第四个局限是 Agent 设计容易停留在命名层面。如果只是把函数叫做 Agent，但没有明确输入、工具、输出、日志和是否调用 LLM，就不符合 Multi-Agent 架构的工程要求。因此我后面专门要求为每个 Agent 增加职责边界和日志记录。

## 四、人工介入最多的地方

人工介入最多的是需求判断。项目需求明确要求“静态分析 + LLM 报告生成”，所以我要求 AI 不能只做一个 LLM 总结器，而要先写确定性分析工具。这个方向决定了整个项目结构。

第二个是架构修正。初始版本更像模块化工具集合，后来为了符合 Multi-Agent 要求，我要求重构成 `Architecture Agent`、`Tech Stack Agent`、`Code Quality Agent`、`Document Agent`、`Summary Agent`、`Comparison Agent` 等结构，并保留 Agent 日志，方便说明每个 Agent 的输入输出。

第三个是运行验证。每次新增功能后，我都需要运行 `python -m py_compile`、`pytest tests` 或启动 Streamlit 检查页面。比如 pytest 误收集第三方仓库测试的问题，如果不实际运行就不会发现。

第四个是内容真实性控制。项目文档中，我刻意避免把项目写得过于理想化。例如依赖健康度、测试覆盖率、RAG 问答质量这些部分都按当前实现能力描述，没有虚构具体覆盖率和漏洞数据。

## 五、效果较好的 Prompt 写法

效果最好的 Prompt 通常有三个特点：目标明确、约束清楚、带现象或错误信息。

例如“请实现代码质量分析，至少支持 Python AST，统计函数数量、类数量、平均函数长度、长函数、长文件、TODO，并输出 100 分评分和扣分原因”，比“帮我分析代码质量”效果更好。前者会让 AI 生成更稳定的结构化结果。

再比如“pytest 会错误收集 `data/analyzed_repos/pallets_flask`，导致 `ModuleNotFoundError`，请只修改测试配置，不要删除缓存目录”，这个 Prompt 同时说明了错误原因、限制条件和期望结果，因此 AI 给出的修复比较准确。

页面优化类 Prompt 也需要具体。例如“右边很满但左边很空”“项目类型和结构模式显示不全，可以改成横向可滑动”“文件树太长，改成纵向滚动”，比单纯说“优化 UI”更容易得到可用结果。

## 六、需要避免的 Prompt 写法

开发过程中我也发现，有些 Prompt 太宽泛时效果不稳定。比如“一次性帮我完成完整项目”容易生成大量代码，但很难判断每个模块是否真的符合题目要求，也容易出现页面能展示但分析逻辑不足的问题。

还有一种需要避免的是只要求“更高级”“更智能”，但不说明智能体现在哪里。对于本项目来说，智能性不是页面上多写几段 AI 文案，而是体现在先提取证据、再由 Agent 分析、最后生成报告。因此 Prompt 必须强调“基于哪些输入分析”和“输出什么结构化结果”。

另外，对于文档生成也不能只说“写得好一点”。更有效的做法是规定章节、字数、不能夸大、不能虚构数据、要结合真实模块和日志。这样生成的报告更接近工程交付文档，而不是普通宣传稿。

## 七、对本项目的帮助

Vibe Coding 对本项目最大的帮助，是让我把精力更多放在系统设计和功能验证上，而不是陷在重复代码和样板文档里。AI 负责快速生成候选实现，我负责判断它是否符合项目目标、是否能运行、是否解释得通。

项目最终形成了“规则工具 + LLM Agent”的混合架构：规则工具保证分析有事实依据，LLM Agent 负责语义概括和报告表达。这个设计比单纯让 LLM 看 README 更可靠，也比完全规则化的工具更适合做自然语言报告和对比建议。

同时，Vibe Coding 也让我更明显地意识到工程验证的重要性。只要涉及本地环境、第三方仓库、文件权限、网络接口和模型服务，就必须通过真实运行确认。AI 可以提供方向，但不能替代测试。

## 八、后续改进方向

如果后续继续完善这个项目，我会优先做几个方向。第一是接入真实向量数据库，例如 ChromaDB，让 RAG 问答从简单关键词检索升级为向量检索。第二是接入依赖漏洞数据库，让依赖健康度不再只是结构性检查。第三是增加更多语言的 AST 或静态分析支持，例如 JavaScript、Java 和 Go。第四是给 Agent 输出增加更严格的 JSON Schema 校验，减少 LLM 输出格式不稳定的问题。第五是增加历史报告管理，让用户可以查看不同仓库、不同时刻的分析结果。

总体来看，Vibe Coding 适合用来提高开发效率，但前提是开发者自己要知道项目目标和验收标准。对于这个项目来说，AI 帮助我完成了大量实现和文档整理工作，但项目能否符合需求，仍然取决于我是否能把需求拆清楚、把功能跑通、把结果讲明白。
