# 课程设计答辩说明

## 本项目解决了什么问题

本项目解决的是“如何快速理解一个陌生 GitHub 仓库”的问题。传统方式需要人工查看目录、依赖、README、测试、安全配置和代码复杂度，成本较高；如果只依赖大模型直接总结，又容易受到上下文长度、幻觉和遗漏影响。本项目通过自动化静态分析生成结构化事实，再结合本地 LLM 生成自然语言报告，让分析结果既可解释又便于展示。

## 为什么不能直接把仓库丢给 LLM

1. 仓库代码量可能远超模型上下文限制，无法完整输入。
2. LLM 对文件数量、目录数量、依赖列表、函数长度等指标不擅长做精确统计。
3. 直接总结容易产生幻觉，报告依据不清晰。
4. 直接上传完整代码可能带来隐私和安全风险。
5. 课程设计需要体现工程实现能力，不能只是封装一个聊天接口。

因此本项目采用“确定性静态分析 + LLM 报告生成”的方案。静态分析负责产生可信事实，LLM 负责组织语言、解释结果和生成建议。

## 静态分析和 LLM 的分工

静态分析部分负责：

- 通过 GitHub API 获取仓库元信息、README 摘要和远程文件树统计。
- 克隆或读取缓存仓库。
- 基于 GitHub 描述、README、topics、包元信息和技术栈分析项目用途、项目类型和目标用户。
- 遍历目录并统计文件结构。
- 识别语言、框架、依赖和工程工具。
- 识别架构模式、入口文件和模块划分。
- 使用 AST 分析 Python 函数、类和函数长度。
- 检查 README、LICENSE、依赖文件和 `.gitignore`。
- 扫描 `.env`、疑似凭据、虚拟环境目录和大文件。
- 生成评分、风险列表和扣分原因。

LLM 部分负责：

- 读取前面模块生成的结构化 JSON。
- 在 Overview、Tech Stack、Architecture 等 Agent 中基于受控证据做语义解释，不直接读取整个仓库。
- 将指标转化为适合阅读的 Markdown 报告。
- 给出新人上手建议和后续改进建议。
- 在 Ollama 不可用时，由模板报告替代，保证系统可运行。

Multi-Agent 部分负责：

- 将结构化分析结果分发给架构、技术栈、代码质量、文档和汇总 Agent。
- 每个 Agent 输出 JSON，记录耗时和 token 估算。
- Dashboard 展示协作日志，方便说明 Agent 间分工。

RAG 部分负责：

- 对 README、配置和代码文件做轻量检索。
- 将用户问题匹配到最相关的仓库片段。
- 对“怎么运行”“数据库模型有哪些”等常见问题给出可追溯回答。
- 如果 Ollama 可用，只把检索到的小片段交给模型，不上传整个仓库。

## 主要技术难点

1. **仓库获取的稳定性**
   - 需要处理 URL 非法、网络失败、Git 未安装、仓库已存在等情况。
   - 项目通过 `repo_loader.py` 统一解析 URL，并提供缓存复用和重新克隆选项。

2. **避免无意义扫描**
   - 仓库中可能包含 `.git`、`node_modules`、`venv`、`build`、`dist` 等大目录。
   - 项目在文件遍历时统一忽略这些目录，提升速度并避免无关结果污染。

3. **代码质量分析的可解释性**
   - 简单统计行数无法体现代码结构。
   - 项目使用 Python AST 统计函数、类和函数长度，并将超长函数、解析错误、测试缺失等转化为扣分原因。

4. **安全扫描的误报控制**
   - token、password、secret 等关键词可能出现在文档或代码示例中。
   - 项目采用规则匹配、文件大小限制和脱敏展示，尽量降低风险，同时提醒用户人工确认。

5. **LLM 退化策略**
   - 课程演示时 Ollama 或模型可能不可用。
   - 项目实现了模板报告 fallback，保证核心功能不依赖外部服务。

6. **Dashboard 产品感**
   - 不能把命令行输出简单搬到网页。
   - 项目使用多栏布局、指标卡片、进度条、Plotly 图表、质量雷达图、文件树、风险表、Agent 日志、RAG 问答和报告导出，呈现接近真实 SaaS 的分析体验。

## 老师可能提问及回答

### Q1：你的项目和“让 ChatGPT 总结 GitHub 链接”有什么区别？

A：本项目不是直接让 LLM 总结链接。系统先用 Python 做确定性静态分析，得到文件数量、目录结构、依赖、AST 指标、文档检查和安全风险等结构化结果；LLM 只基于这些结果生成报告。因此报告有明确依据，统计指标可复现，且 Ollama 不可用时仍能输出模板报告。

### Q2：为什么使用 AST 分析 Python 代码？

A：AST 能识别函数、类和代码结构，比单纯按文本或行数统计更可靠。本项目通过 AST 统计函数数量、类数量、平均函数长度和超长函数，从而形成可解释的代码质量评分。

### Q3：技术栈识别是怎么做的？

A：项目采用规则识别。比如 `requirements.txt`、`pyproject.toml`、`setup.py` 表示 Python 工程；`package.json` 表示 Node 项目，并可进一步识别 React、Vue、Express、Vite；`pom.xml` 和 `build.gradle` 表示 Java 工程；`Dockerfile`、`docker-compose.yml` 和 `.github/workflows` 分别识别 Docker、Docker Compose 和 GitHub Actions。

### Q4：如果 Ollama 没有启动怎么办？

A：系统会捕获 Ollama 请求异常，并自动切换到模板报告模式。静态分析结果、评分、风险表和导出功能仍然可用，因此演示不会因为 LLM 服务不可用而中断。

### Q5：安全扫描会不会误报？

A：会有一定误报可能，因为静态规则无法完全判断字符串是否真实凭据。本项目通过严重程度分级和脱敏展示提醒用户人工确认。答辩时可以说明这是轻量级安全检查，不替代专业 SAST 或密钥扫描工具。

### Q6：评分标准是否客观？

A：评分是启发式规则，重点是可解释和可扩展。例如测试缺失、超长函数、超长文件、TODO 标记和 AST 解析失败都会扣分，每个扣分项都会展示原因。后续可以引入复杂度、覆盖率和 lint 工具进一步优化。

### Q7：为什么选择 Streamlit？

A：Streamlit 适合快速构建数据分析 Dashboard，支持输入框、按钮、进度条、指标卡、表格、图表和 Markdown 展示，能在较短课程周期内实现可交互、可演示的 Web 产品。

### Q8：Multi-Agent 是怎么体现的？

A：项目实现了逻辑 Multi-Agent 编排。架构 Agent、技术栈 Agent、代码质量 Agent、文档 Agent 和汇总 Agent 分别处理不同结构化输入，输出 JSON。其中架构、技术栈、概览和汇总 Agent 可以调用 Ollama，但只接收规则工具产出的受控摘要。Dashboard 会显示每个 Agent 的输入摘要、输出、耗时和 token 估算。这样可以体现 Agent 分工与汇总过程，而不是一个函数直接生成所有结论。

### Q9：RAG 问答如何避免胡编？

A：RAG 模块先从仓库 README、配置和代码中检索相关片段，再回答问题。如果调用 Ollama，也只发送 Top-K 片段和仓库摘要。回答会展示检索来源，便于人工核对。对于“怎么运行”“数据库模型有哪些”等问题，还加入了确定性启发式分析。

### Q10：GitHub API 和 git clone 为什么都要用？

A：GitHub API 适合快速获取仓库元信息、README 和远程文件树；git clone 适合做本地 AST、代码质量、安全扫描和 RAG 检索。两者结合既满足 API 获取要求，也保证深度静态分析能力。

### Q11：系统怎么判断一个仓库是干什么的？

A：项目用途分析先使用确定性模块读取 GitHub API description、README 标题和开头段落、仓库 topics、`package.json` 或 `pyproject.toml` 描述，再结合技术栈和架构模式生成基础判断；启用 Ollama 时，Overview Agent 只基于这些受控证据补充语义解释。Dashboard 会展示证据来源，用户输入链接后第一屏就能看到“这个仓库是做什么的”。

## 后续优化方向

- 增加更多语言的 AST 或语法树分析，例如 JavaScript/TypeScript、Java、Go。
- 使用 ChromaDB 替换当前轻量检索，实现向量 RAG 和语义检索。
- 接入 Radon、Ruff、Bandit、Semgrep 等专业工具增强质量和安全分析。
- 增加 Git 历史分析，例如提交频率、贡献者、热点文件和最近维护情况。
- 支持私有仓库授权分析，但需要严格保护 token 和本地凭据。
- 增加报告对比功能，支持同一仓库多次分析后的质量变化趋势。
- 增加异步任务队列，避免大型仓库分析时阻塞页面。
- 增加 Docker 部署文件，方便在统一环境中演示。
